# 模型排名与纯脚本 AI 联赛：审计方法

这份文档说明如何判断“小模型击败大模型”是否有合理来源，以及如何复跑和阅读证据。最终数值以冻结版本运行生成的 `summary.json`、`summary.md` 和八个压缩原始块为准。本文件不会用早期候选版本的结果代替最终验收。

## 1. 需要分别回答的问题

以下六种结果不能合并成一句“小模型登顶”：

| 结果 | 比较对象 | 它能说明什么 |
|---|---|---|
| 同期历史综合 SOTA | 当月完整历史目录中所有可见型号的最高综合 Q | 是否超过游戏记录的同期行业前沿 |
| 脚本联赛综合第一 | 同剧本、同 seed、同策略、同月、同模态，各公司的最强已发布型号 | 在指定控制策略和初始资源下谁更强 |
| 当月在线阵营第一 | 上一项进一步排除已经退出的公司 | 当时仍在经营的公司中谁更强 |
| 专项榜第一 | 同一个基准的成绩，包括合理并列 | 某一项任务的相对能力，不自动提高综合 Q |
| 小模型击败大型记录 | 小模型与其他公司的最强已发布记录比较，对方记录总参数大于 100B | 是否存在代际、数据、训练或榜单口径值得复查的差异 |
| 性价比或调用量第一 | 市场需求、成本、价格或流量指标 | 商业竞争表现，不授予综合 SOTA |

综合 SOTA 对照包含正在扮演的公司在历史目录中的型号，避免选择某个角色后行业基准自动降低。历史目录是比较标尺；它不因此成为当前存档中可以凭空调用的自家老师。老师可用性另由游戏实际发布状态、开放性及数据来源规则决定。

## 2. 三层证据

### 2.1 历史目录和榜单的穷举扫描

`scripts/audit_model_rankings.mjs` 遍历 2023-01 至 2026-10，检查全部模态、公司视角、榜单及分类过滤。它把引擎返回值与枚举当月所有可见历史型号得到的独立答案比较。

主要检查：

- 最新在售型号与能力最强型号是否被混淆；发布较弱新版本不应抹掉较强旧版本的能力纪录。
- 综合榜、专项榜、开源老师与分类榜，是否先按相应条件筛选再取最强。
- 参数分类是否采用总参数；MoE 激活参数只影响相应计算成本，不能把大型 MoE 伪装成超小模型。
- 同分是否获得相同名次；名次采用 `1, 1, 3`，不靠数组顺序强分胜负。
- 基准量程下限为 0.0 时的并列，是否被误称为独占第一或综合突破。
- 读取榜单、预览和比较函数是否改变游戏状态或 RNG。

这个扫描验证历史数据和榜单逻辑。它不会实际训练新模型，所以还需要下面的完整对局和定向极限路径。

### 2.2 完整独立对局

正式矩阵为：

| 维度 | 取值 |
|---|---|
| 公司 | 游戏中的全部 24 家公司 |
| 年代剧本 | `y2023`、`y2024`、`y2025`、`y2026` |
| 随机种子 | `1, 7, 19, 42, 71, 186, 2026, 65537` |
| 控制策略 | `balanced`、`tiny` |
| 完整独立游戏数 | 24 × 4 × 8 × 2 = **1,536** |

每局有独立存档、操作、研发状态和随机序列。各局运行结束后才横向比较同月能力；这不是同一个存档里有 24 个自主研发对手，也没有跨局实时传递老师、资金或模型。

两种策略都使用 `historical` 商业模式，以隔离研发和榜单行为。反应式商业对手有独立的集成测试，不把它的价格反应误当作研发能力。初始旗舰、已有训练项目、现金、算力和公司差异均按剧本保留；没有把所有参赛模型重置成 3B。

**`balanced`：常规目标策略。** 复用 `tests/helpers/career_bot.mjs`。每周检查目标、技术、数据、算力、项目和发布条件。它保留既有测试机器人直接调整推理占比、记录内部操作标记的少量行为，因此不宣称所有步骤都等同于点击 UI。模型训练、数据、发布等关键行为经过引擎规则。

**`tiny`：3B 优先压力策略。** 使用独立脚本，通过公开操作优先选择合法的 3B 预训练或 3B 蒸馏学生；RWKV 采用相应循环架构。它检查数据量和项目耗时，沿用顾问处理经营及后训练，并在可发布时发布。其他模态选择可用最小预设。它不直接改现金、模型维度、已有旗舰或 seed。该策略用于施压容量、老师和来源规则，不是最优小模型商业策略。

每局持续到正常终局、董事会目标失败、破产或异常终止。驱动有 2,500 天的上限；仍为 playing 的局会记为未终止错误，不能混入成功完成。目标失败和破产是游戏结局，分别统计；它们也不能冒充到达 2026-10。

### 2.3 定向可达路径与数值边界

完整联赛只覆盖两种控制策略。它没有找到某条路线，不能证明那条路线不存在。`scripts/audit_scaling_balance.mjs` 与 `scripts/audit_repeat_sensitivity.mjs` 补充检查极端规模、老师、重复语料和可实际发布的训练路径。

特别保留对 3B、7B 和 14B 的实际从零训练检验。不能为了让报表全绿而按公司名或 small 标签强行禁止获胜。若 14B 在特定公司资源、数据和早期时间窗口下取得合理的综合优势，应给出维度、成本、时间和同期对照解释。重复语料收益参数属于游戏校准，不是现实世界的训练定律。

## 3. 怎样采样，怎样保存来源

月度回调在游戏实际运行中采样，而不是拿终局模型倒推之前的月份。退出时补充该局的末次采样；`monthClosed` 区分完整月结和退出当月的部分月。未发布 working 模型不参加比较。

模型证据包括：

| 字段 | 用途 |
|---|---|
| `total`、`active`、`arch`、`cls` | 核对总参数、激活参数、架构和分类 |
| `dims`、`base`、`capTechs` | 核对综合能力与能力来源 |
| `pretraining` | 实际预训练数据和训练记录 |
| `distillation`、`teacher` | 学生蒸馏所用老师及其快照 |
| `dataDistillation` | 蒸馏语料的来源与实际增益 |
| `eventLearning` | 剧情或里程碑直接给予维度增益的事件、选择、日期与实际增量 |
| `released`、`releasedDay` | 型号在该局何时发布 |
| `origin`、`inherited`、`structureSource` | 区分剧本继承底座、模拟预训练、模拟蒸馏及估计结构 |
| `benchmarks` | 该型号真实保留的评测纪录 |

开局已经发布的型号，以及开局已有但稍后才发布的训练底座，都不能冒称由本次机器人从零训练得到。脚本保留这些型号参与能力比较，同时把来源标为继承。旧存档缺少细粒度账本时，也保留来源不明确这一事实。

同一型号在真实评测纪录等状态发生变化后，可以对应多个快照。`storedModelSnapshots` 是快照数；`distinctReleasedModels` 按独立局和模型 ID 去重，才是不同已发布型号数。

## 4. 综合比较、专项复测与并列

每个比较组由“剧本 × seed × 策略 × 月份 × 模态”确定。先找每家公司全部已发布型号中综合 Q 最强的型号，再跨公司比较。公司退出后，其已发布能力纪录冻结保留，并按比较月份的同一评分标尺重算；另列当时仍在经营的公司的冠军。

综合 Q 在审计输出中量化到小数点后六位。分数相同的公司都列为冠军；只有一家公司的最高分独占第一，才计入 `Outright`。游戏专项榜的分数按现有基准精度量化，并采用同分同名次。单项 0.0 并列另设标记，不能称为独胜。

小模型与大模型比较中的“大型代表”，指被选为某公司最强综合记录、且总参数大于 100B 的型号。`smallBeatsSomeLarge` 表示至少击败另一个公司的大型代表；`smallBeatsBestLarge` 还要求击败该比较组所有公司、**包括自身公司**的最强大型代表。辅助异常复核另列“先排除自身公司，再取最强大型对手”的指标，两者必须明确命名，不能混用。它们都不等于击败完整历史目录，也不等于所有存在过的大型型号。

专项证据有两条独立来源：

- `benchmarks` 与月度 `published` 保存游戏中实际产生并保留的成绩。
- 月度 `scores` 通过公开评测函数，在隔离的状态副本上使用统一 RNG 复测。它用于比较同样评测条件下的能力，**没有**替玩家支付或发布一次评测，也不消耗真实局内 RNG。

同一公开结果可能连续多月被观察到。报告分别给出观察次数和去重后的真实结果数；前者不能充当独立评测次数。固定 RNG 复测也不能冒充真实玩家已经公布的成绩。

## 5. 报告的计数单位

| 计数 | 单位与解释 |
|---|---|
| 独立游戏数 | 公司 × 剧本 × seed × 策略的唯一组合 |
| 月度观察数 | 某局一次真实月结或退出采样 |
| 比较月数 | 同剧本、seed、策略、月份、模态的一次横向比较 |
| 小模型冠军月数 | 一个比较月里至少有一个满足规模阈值的冠军；包括并列 |
| 独胜月数 | 一个比较月里只有一家公司的记录最高 |
| `flagCounts` | 待复查的公司模型/月份或专项实例，可能跨月重复 |
| 历史 SOTA 超越月数 | 一个 LLM 比较月里，最强对应规模型号严格超过完整历史目录最高 Q |

脚本保存每类前 100 个具体 flag 例子，但计数覆盖所有实例。完整模型和月度样本保留在压缩块中，可重新计算。摘要例子不是全部异常全集，也不该把成百上千个跨月 flag 说成成百上千个独立漏洞。

对“超小模型赢大模”的复核进一步从全部原始月度快照重算，不局限于前 100 个例子：按 ≤3B 与其他公司 >100B 的最强实际记录配对，找最大差距、对最强大型记录的领先及来源特殊的代表，检查双方版本、继承/训练、老师、事件增益和退出状态。最终结论采用可复查的规则分类、极值检查和代表复核；不会声称人工逐条阅读了全部跨月 flag。

## 6. 复跑与版本验收

在项目根目录，一次完整复跑：

```bash
node scripts/audit_ai_league_batch.mjs --run --out-dir /tmp/ai-league-1536-final
```

若执行环境不允许 Node 创建子进程，可分别直接运行八次主脚本。例如第一个 seed：

```bash
node scripts/audit_ai_league.mjs --seeds 1 --out /tmp/ai-league-1536-final/seed-1.json.gz
```

另外七次分别使用 seed `7, 19, 42, 71, 186, 2026, 65537` 和对应文件名。全部完成后，仅聚合已有结果：

```bash
node scripts/audit_ai_league_batch.mjs --out-dir /tmp/ai-league-1536-final
```

验收同时检查：

- 24 家公司、4 个剧本、8 个 seed、2 种策略的组合完整，且没有重复局号。
- 每块运行前后所有引擎、数据、机器人和主审计驱动的 SHA256 一致。
- 八块的依赖清单完全相同，当前源文件与被测文件一致。
- 批处理脚本自身在聚合期间没有变化。
- 无 NaN/Infinity、非法模型结构、越界维度、审计污染 RNG、崩溃或未终止错误。
- 策略操作错误独立计数，不因游戏最终退出而被抹掉。

每块保存时间戳、Node 版本、实际参数、逐文件散列和依赖清单散列。若运行中源文件变化，该块保留为候选证据并标为失败；不能把新旧版本混合成最终验收。

## 7. 结论的边界

历史日期仍按月处理，无法证明真实发布日期在同一个月内的先后可见性。报告只验证游戏目录中的这些记录，不对每个真实参数或实测分数做外部考证。

综合 Q 从 2024-06 开始纳入 Agent 维度。相同维度向量在这个月切换前后可能得到不同绝对分数；本审计采用同月横向比较，避免把标尺变化误说成模型退步。

LLM 的 small/mid/large 分类按总参数判断；≤3B 是本次压力检查额外使用的“超小”阈值。部分未公开结构采用游戏估计。带有 13B 激活参数的大型 MoE，不会被当成 13B 总参数小模型。

八个 seed 能检查事件、随机失败和策略路径的差异，但不是独立同分布样本的统计证明。两个控制策略也不是穷举最优求解器。没有观察到某种漏洞，只能表述为在这份矩阵及对应代码版本中没有观察到；定向测试中可达的合理小模型突破应另行保留。

小模型凭借更新的数据、更合适的训练、教师能力或专项优势胜过旧大模型，可以是正常玩法。审计关注的是无来源能力、错误分类、旧旗舰纪录被抹去、榜单比较对象改变、并列被强排及不支付成本等问题，而不是把一切小模型获胜都视为错误。
