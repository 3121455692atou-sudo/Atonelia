# v0.9.2 外部改动包审查结论（给制作人）

## 先说结论

**建议挑着合并，不整包收。** 要收的部分在 v1.0 开工第一步（P0.1 生成指纹和 v3 存档夹具）之前一次合完。合完重跑校准，把规格 F4 里的"v0.9 基线"换成新数字。不收的部分只拿来参考。

- **不整包收**，原因有五个：
  - 董事会撤换局数翻倍；
  - 96 局平均月收入降了约三成半，史实上定高价的开局降一半以上；
  - 小公司下一单开源蒸馏，要停训一年多；
  - 反应式对手和客户分组定价都在 v1.0 规格之外；
  - 单局变慢 2.4 倍。
- **也不只看不用**，原因有两个：
  - 它修好了十几个能在 BASE 上复现的真 bug；
  - 有几块正好是 v1.0 规格本来要做的：D1 取家族最强、D7 立项时冻结老师快照、E9 出租卡数钳制、B3 榜单开源列。等 P0.2a 把 game.js 拆开以后再挑，会难很多。

严重程度分三档：严重 / 一般 / 轻微。复核员意见不一的标"待定"。被复核推翻的发现，本文不再当问题提。

## 一、整包实测（主会话数据）

| | v0.9（BASE） | v0.9.2（NEW） |
|---|---|---|
| 机器人 384 局 | S6 A30 B68 C108 D87 E47 F27 G11，撤换 31（8.1%） | S4 A27 B33 C101 D98 E62 F40 G19，撤换 57（14.8%） |
| 大按钮 384 局 | S8 A44 B99 C138 D45 E40 F4 G6，撤换 12（3.1%） | S8 A37 B62 C117 D82 E41 F24 G13，撤换 27（7.0%） |
| 单局机器人耗时 | 约 116 ms | 约 274 ms |
| calibrate 全程 | 63 s | 128 s |

两边都是 0 报错。按 F4 的目标线，NEW 有三项超标：
- 机器人撤换 14.8%，目标 ≤8%（BASE 的 8.1% 本身也略超）；
- 机器人 F+G 占 15.4%，目标 ≤12%；
- 大按钮撤换 7.0%，目标 ≤6%。

各切片复核已经把原因拆清楚了：

- **撤换翻倍，大头来自"技术上限去重"（capTechs）。**
  - 只把 model.js:114 改回旧写法，照大按钮玩的 192 局里失败从 12 局降到 4 局，y2026 剧本的 8 局全部恢复。
  - 过程以文心 y2026 为例：开局模型的成长上限变低（Agent 上限从 99 降到 82）。顾问判断这代底座够不着 SWE-bench Pro，开局第一天就劝立 1600B 新底座。新底座练出来只有 Q70，比在线的文心 5.1（Q82）还弱，顾问却按"后训满 6 个月就发"把它发了出去。月收入从 870 万掉到 380 万，最后被撤换。
- **收入大降，大头来自客户分组定价。**
  - 只把定价模型换回旧的，GPT y2024 月收入从 1.2 亿回到 4.3 亿。整体收入降幅里，约六到七成出自这一项。
  - 它不是撤换翻倍的原因：换回旧定价后，撤换是 15 局，NEW 原样是 14 局，BASE 是 8 局。
- **其余原因**：开局沿用了史实旗舰档，而新定价下旗舰档基本是亏的；预训练的几项数值改动全部退回后，768 局里撤换从 115 降到 102。
- **变慢的原因**：bestRelease 和榜单每次都把整张表扫一遍、逐条打分，这部分自身约占 24% 的耗时；另有 15–20% 来自 NEW 的机器人每周反复调用顾问。

**浏览器实测（接上真美术资源）：**
- 标题、选公司、主界面立绘、剧情演出、服务页报价预估、对手页回应卡都正常；375px 宽度无横向溢出；存档重载正常。
- 缺图兜底在真图存在时不会把真图顶掉。
- 对手页仍显示 o1 综合 74.6 落后于玩家的 R1 76.4。这是综合分口径的老问题，BASE 一样有，NEW 没修，留给 v1.0 的 qOf。

## 二、按改动组的合并方案

### A. 直接收

1. **公开命令输入校验、出租卡数钳制、走私卡记账、备案文案**
   - 修的都是真 bug：
     - BASE 里调用 setInferShare(NaN)，训练算力变成 NaN；
     - 出租 −100 万张卡，训练算力放大 75 倍；
     - 走私卡下单时记一次、到货再记一次，被海关扣了也算持有，之后"走私曝光"会按根本不存在的卡去没收；
     - 备案文案写"不低于 55"，实际门槛是 50。
   - 已核对界面和顾问传进来的值都在白名单内，不会误伤正常操作。对应规格 E9 和 P0.3b。
2. **逐日算力账单 + 先划出租卡、再分推理和训练**（economy.js:224、model.js:141）
   - 堵住了 BASE 里四个能白拿钱的漏洞，见第四节第 1、2 条。旧档当月按天折算，没发现账对不上。
   - 合并时要把 gpuAllocation 里"数据生成"那一桶去掉，因为生成任务这次不收。
   - G6 切片主张留到 v1.0，理由是会改平衡。我判断现在就收：它改的是漏洞，对平衡的影响很小。
3. **economy 两处小修**：没有在线模型时，出租卡收入照常入账（BASE 里等于白干）；有需求但没有推理卡时，429 率取 1。
4. **董事会目标说明文案**（app.js:583）：BASE 写的是"项目终止"，实际规则是累计三次警告就撤换。
5. **主屏芯片条和新闻条改为顺排**（career.css:755–756）：BASE 的新闻条钉在 top:46px，芯片一折成两行就会压在一起。

1. **模型结构统一解析**（新文件 data/model_structure.js）

     - 榜单下方的说明段落太长，还写着"SOTA""量程下限"。改成"综合最强""最低分"，只在真有并列时才显示（G4-16，一般）。

### C. 留到 v1.0 再说

1. **技术上限去重（capTechs）**
   - 方向就是规格 D6。"从零预训练的新底座，技术快照记为空"这个处理，比规格里写的更合理。
   - 不现在收的原因：它是撤换翻倍的大头，现在合进来会把问题带进 P0.1 的基线。要它不出事，得同时改顾问、重标目标，这是 P1.2 和 P4.2 的活。到 P1.2 做 D6 时，直接参考 NEW 的实现。
   - 这和 G6 切片"直接收"的意见不同，我按 G5-5 的复现结果改判。
   - 要先在规格里解决三件事：
     - 开局继承的"训练中"史实下一代，知识上限正好等于开局值，往知识方向后训练一点都不涨。y2024–y2026 几乎所有文本模型公司都这样。例如 DeepSeek-V3-0324 知识上限 83，史实值 86，用史实型号名发布时永远够不到（G1-2、G2-4，待定：复核员一半判严重，一半判一般）。规格 D6 用的是同一个公式，照着写也会出这个问题。改法：调大 HEADROOM.knowledge，或者让开局继承模型的知识 base 少减一点。同时加一条测试："y2025/y2026 的继承在训模型，各维上限不低于史实发布值"（y2023/y2024 在 BASE 里本来也差 1–3 分）。
     - 顾问不能把比在线旗舰弱的新底座发出去。一位复核员实测到一句自相矛盾的建议："要求 ≥15%……练满也只有 17.6% 左右，得换更大的底座"，这个判断也要修。
     - 依赖新上限的董事会目标（g26_swepro、g26_gdpval 等）在 P4.2 重新标定。
2. **数据生成任务**（generation.js、生成订单占训练卡、暂停和继续、顾问的暂停建议、ui/orders.js 状态文案）
   - "生成数据要真花算力"这个方向是对的，也补上了 BASE 里合成教材的 computeH100 字段从来没生效的问题。
   - 但现在小公司根本用不了：
     - 生成任务排在训练前面，能把训练卡全部吃光；工作量是写死的，不看公司大小（G1-1，严重）。
       - RWKV y2025 下一单开源蒸馏，训练连续停 67 天。
       - 2023 剧本里只有 96 张 A100 的小公司，要停训 420 天左右；RWKV 要约 600 天。
       - BASE 是两周到货，训练照常。
       - 订单不能取消，暂停以后也不能重新下单。
     - 顾问让小团队暂停之后，几乎永远不提示恢复：恢复的条件是"恢复后训练还剩一半卡"，小团队达不到。暂停的订单还会压住其他数据建议（G3-5，待定）。

## 四、确实修好的 BASE 真问题

以下都在 BASE 上复现过：

1. **算力账单的四个漏洞**
   - 月底最后一天退租，整月 135 万的租金变成 0；
   - 月底最后一天才出租 3000 张卡，照收整月 378 万；

   - 推理份额 0.9 加出租 80% 时，出租卡被同时算进推理：推理当量算成 19312，正确值是 3862。
